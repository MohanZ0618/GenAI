# Evaluation

Run `npm run evaluate` for the prepared reference cases, or append `-- development`, `-- heldout`, or `-- stress`. Fixture reports are deterministic financial verification results with measured runtime variability. The report records provider, model, mode, query counts, source citation validity, reference evidence recall/precision and technical failures.

The last completed offline run matched 39/40 development outcomes, 20/20 held-out outcomes and 10/10 derived coverage-stress outcomes. There were no technical failures, no normal-case false positives in the 12 normal reference cases, and all displayed citations resolved to retrieved records. One development case remained unresolved; it is retained in the results rather than discarded.

These numbers do not prove performance on real business data or unseen financial workflows. The sample is small, deterministic, selected from supported categories and shares generator assumptions with the verifier. The ten stress cases are correlated transformations, not ten independent natural incidents. Root-cause accuracy is category-level, not a judgement of prose quality.

The fixed rules baseline receives the complete visible packet. Fixture orchestration uses those same verification rules, so identical outcomes are expected and cannot demonstrate an AI advantage. The live evaluation additionally executes a one-pass response with the same configured model, the full visible packet, no remembered case answer, and strict citation validation. The full live reference-set comparison has not been run. PostgreSQL, Zetaris and OpenAI connectivity and selected live business cases have now been verified; missing configuration is no longer the reason this comparison remains open.

Citation precision counts cited records against the benchmark's minimal required record IDs; useful supporting records outside that minimal set can lower this number. Evidence recall counts required source IDs present in cited records, including journal aliases. The evaluator does not reward fabricated records or failed-query absence claims.

Unit and integration tests cover schema validation, exact monetary parsing, referential integrity, immutable versions, source gaps, currency boundaries, constrained model tools, transient model failures, namespace-isolated persistent H-MEM, run lifecycle, review and exports. Browser tests cover the desktop workflow, refresh recovery, mobile overflow, and import errors. Selected live acceptance is complete; full live evaluation and real-user value remain separate gates.

## Business acceptance on 2026-10-26

`npm run verify:business -- --repeat=3` runs nine selected synthetic scenarios, plus two additional rounds of normal, duplicate-payment and partial-coverage cases (15 runs total). Use `FINTRACE_MODE=fixture` for offline validation. In `live` or `local-model`, add `--connect` explicitly; those modes make billable model calls. Live requires the existing configured PostgreSQL and Zetaris services. Run while other investigations are idle.

Both fixture and live acceptance passed 15/15. Live used OpenAI `gpt-5.4-mini` (returned model `gpt-5.4-mini-2026-03-17`), PostgreSQL storage and Zetaris evidence retrieval. The 15 live runs recorded 65 successful model HTTP requests, 109989 reported tokens, and 80 successful application-level evidence-tool queries. A tool query may read several tables; these are not 80 individual SQL statements. The preflight model request is separate from these totals.

The script checks completion, expected outcome/category, citation resolution, evidence-query status and model activity, and uses fresh namespaces to prevent old result reuse. Raw run exports and incremental summary files are written only under ignored `.local/business-cases-*` directories. Trace query IDs are generated by the application, not returned by the Zetaris server. These are selected acceptance cases, not independent samples or a blind held-out evaluation.
